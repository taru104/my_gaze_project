# Qiita 記事戦略 — 何が伸びているかの分析

> 調査日 2026-08-06。**実測・出典ありの事実**と、**私の推論**を必ず区別して書く。
> 推論には「〔推論〕」を付ける。鵜呑みにしないための措置。

---

## 0. 結論（先に）

Tgaze の記事は「**作ったので見てください**」型では伸びない。実際、Qiita の全記事分析で
「あからさまにアプリ作ったから見に来てね的な記事はあまり伸びていないが、技術要素を紹介している
記事はバズっている」と明言されている（出典①）。

一方で、**この分野には明確な空席がある**。MediaPipe で視線 UI 操作を試して
「**精度が足りず実用にならなかった**」と結論した記事が実在する（出典④）。
Tgaze はその問題を実際に解いた側にいる。

→ 書くべきは **「なぜ MediaPipe の視線推定は精度が出ないのか、原因を特定した話」**。
Tgaze はその論拠として登場させる。主役は Tgaze ではなく **問題と原因**。

## 1. Qiita の露出メカニズム（出典②③）

- **LGTM 10 が最初の関門**。LGTM 10 超えは全体の上位 20%。
  10 を超えたあたりで「デイリーの LGTM 集計」に載り、そこからデイリートレンド（最も目立つ枠）へ。
- つまり**段階的な増幅構造**で、**初速がすべて**。最初の数時間で 10 に届くかで結果が変わる。
- フォロワーがいると初期露出が増えるので 10 到達確率が上がる。
  〔推論〕ユーザはフォロワーが少ないはずなので、**X からの流入で初速を作る**のが現実的。
  Qiita 単体で自然に 10 に届くのを待つより、投稿直後に X で流す方が確実。

## 2. 定量的な傾向（出典①：Qiita 全記事のデータ分析）

| 項目 | 最適とされる値 |
|---|---|
| タイトル長 | **20〜36文字**（一般的なSEOの32文字目安とも整合） |
| 本文長 | **〜10,000文字**まで LGTM と正相関。それ以上は頭打ち／分散大 |
| 投稿タイミング | **月曜 7〜8時**が平均 LGTM 最高。朝 > 夜 |
| 週末投稿 | 本文は長くなるが LGTM は落ちる |
| 強いタグ群 | 機械学習系（自然言語処理・ディープラーニング・データ分析）、初心者向け系 |

**注意**: これは相関であって因果ではない。〔推論〕「月曜朝に投げれば伸びる」のではなく、
「平日の朝は通勤時間帯で技術記事が読まれやすい」という交絡だと考えるのが自然。
時間帯を最適化しても中身が弱ければ伸びない。**効果量も不明**なので、
時間は「合わせられるなら合わせる」程度の優先度でよい。

## 3. タイトルの型（出典⑤：6つの技法）

1. **速度感を出す**（「爆速で〜」）
2. **数字を入れる**（「19個の奥義」「32選」）— 読む前に分量が分かる。最も簡単で効く
3. **記事の一番尖った部分をタイトルに出す**
4. **初心者を含める**（「初心者向け」「ハンズオン」）
5. **まとめ記事にする**
6. **常識を否定する**（「お前らの〜は間違っている」）— ただし釣りに近いと著者自身が注記

**Tgaze への適用**〔推論〕:
- 使えるのは **2（数字）**、**3（尖った部分）**、**6（常識の否定）**。
- 1（爆速）は内容と合わない。4（初心者向け）は嘘になる。5（まとめ）も違う。
- 6 は自分自身に向ければ釣りにならない。**「自分の指標がバグっていた」は
  自分を否定しているので、他人を煽る 6 の悪い面が出ない**。ここが本記事の強み。

## 4. この分野の現状（実際に検索して確認）

Qiita / note で「MediaPipe × 視線」系に存在する記事:

| 記事 | 内容 | 到達点 |
|---|---|---|
| ARKit と MediaPipe のフェイストラッキング比較 | 顔追跡の比較 | 視線の画面座標には踏み込まない |
| VRChat 用フルトラを WebカメラとMediaPipe で | 体の追跡 | 視線ではない |
| Unity で MediaPipe → VTuber | 顔・視線の「検出」 | 表現用途。精度は問わない |
| **MediapipeによるアイトラッキングでUIの操作は可能か？**（出典④） | **視線でUI操作を試作** | **「細かい操作は難しい」と結論** |

**出典④で報告されている具体的な失敗**（ここが最重要）:
- 画面中心でキャリブしても**パーティクルが動き続ける**（ジッタが取れない）
- **5fps** しか出ず不安定
- 結論:「**実用には projection transformation と、虹彩がもっと精細に写るカメラ構成が要る**」

→ **空席の正体**: 「MediaPipe で視線は取れる」記事は複数ある。
だが「**画面座標を実用精度で出す**」に到達した日本語記事が見当たらない。
そして**到達できなかった記録は公開されている**。

〔推論〕この構造は記事にとって理想的。読者の中に「自分も試して諦めた」層が実在し、
その人たちに「原因はこれでした」と示せる。共感 → 納得 → LGTM の動線が最短。

## 5. Tgaze の記事はどう書くべきか

### 主役は Tgaze ではなく「原因」

タイトル案（20〜36文字を意識）:

| 案 | 文字数 | 狙い |
|---|---|---|
| **MediaPipeの視線推定で精度が出ない原因は、たぶんそこじゃない** | 30 | 技法6（常識の否定）+ 出典④の層に刺さる |
| **webカメラの視線推定を詰めたら、自分の評価指標がバグっていた** | 30 | 技法3。自己否定なので嫌味がない |
| **視線推定で67回実験して、効かなかった手法を全部書く** | 27 | 技法2（数字）+ 負の結果の価値 |

〔推論〕**1案目が最も伸びる**。出典④のような「試して諦めた人」に直接届き、
かつ「そこじゃない」が具体的な中身（画像中心 vs 目頭基準）を持っているので釣りにならない。
ただし**ユーザ本人の書きたいこと**と合うかは本人判断。2案目は内容に一番忠実。

### 構成（本文 6,000〜10,000字を目安）

1. **掴み** — 「MediaPipe で視線は取れる。でも画面座標にすると精度が出ない」という
   よく知られた壁を提示。出典④のような先行事例に触れる（**敬意を持って**。
   「あの人は間違っていた」ではなく「同じ壁にぶつかった」と書く）
2. **原因1: 特徴量** — 画像中心基準 → 顔位置センサー化（相関 0.98 vs 0.48）→ 9cm→1.4cm
3. **原因2: 指標** — 自分の cm 換算が縦を 1.68 倍に水増ししていた
4. **数値と体感の食い違い** — 画面外ジャンプ 11.9%→6.3%
5. **効かなかった手法** — リンバス楕円、解像度上げ、交互作用項
6. **実験設計を間違えて結論を撤回した話**
7. **現在地** — 度での比較（5.73°）。「SOTA超え」とは書かない
8. **ライセンスの明示**

### 削るべきもの〔推論〕

- Tgaze の機能紹介・使い方 → **不要**。読者が持ち帰るのは知見であって使い方ではない
- 「スターください」 → **逆効果**（出典①の「見に来てね記事は伸びない」に該当）
- 経緯の時系列全部 → 冗長。**原因と結論だけ**残す

## 6. ライセンスの扱い（重要・前回の私の説明の訂正）

**訂正**: 私は以前「ライセンスのせいで読者が動かせない」と書いたが、これは不正確だった。
技術的には `git clone` → `pip install -e .` → `python main.py` で**普通に動く**。
ライセンスがしているのは「**許諾なしに実行するとライセンス違反になる**」という法的な制約であって、
動作を妨げるものではない。

記事での扱い〔推論〕:
- **末尾に自分から明示する**。隠して後で気づかれる方が確実に心証が悪い。
- 書き方は「**読むのは自由 / 動かすなら issue で一声 / 商用は不可**」。
  NOTICE.md に「非商用で妥当なら基本 yes」と書いてあるので、**門前払いではない**ことも添える。
- 〔推論〕Qiita は「動かして試す」より「読んで学ぶ」文化が Reddit/HN より強いので、
  知見共有型の記事ならライセンスは大きな減点にならない。
  ただしこれは私の印象であって、データで裏を取ったわけではない。
